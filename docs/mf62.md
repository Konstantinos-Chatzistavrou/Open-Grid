# MF 5.2 / 6.1 / 6.2 tyre evaluator (`rs::mf62`)

`core/include/rs/mf62.hpp` + `core/src/mf62.cpp`: the complete steady-state Pacejka Magic Formula, version 5.2 (and PAC2002), 6.1 and 6.2, with a reader for
real tyre property files (`.tir`, FITTYP 5 / 6 / 21 / 61 / 62). One call gives all 30 MFeval outputs: Fx, Fy, Mx, My, Mz, effective and loaded radius, deflection,
contact patch, pneumatic trail, friction coefficients, stiffnesses and relaxation lengths, with combined slip, camber, inflation pressure, low speed and (optionally) turn slip.

## What the golden test caught

The first comparison, on MFeval's example tyres, passed everywhere. The golden test on the committed tyres then failed on exactly the 17 turn-slip points, in `Mz` and `Mzr` only. Interrogating the real `calculateMz0`
under Octave showed every intermediate equal except `Cr = zeta7 = (2/pi) acos(Mzp90 / |Drp|)`: when that ratio is beyond +-1, MATLAB's `acos` is **complex**, `cos(Cr x)` is evaluated with the complex `Cr`, and only
the final result goes through `real()`. The first version clamped the ratio (and a code comment claimed that gives the same real part, which is false). Now `Re cos(a + ib) = cos a cosh b` is evaluated exactly. The example tyres
never reached that branch, which is why a second, differently-built tyre set is worth having.

## What the comparison does and does not show

It shows that `mf62.cpp` is a faithful port of MFeval's `Solver.m` for those three tyres and 393 points each, including the low-speed, reverse, no-load, out-of-range, alpha*, limits-off and turn-slip branches.
It does **not** show that MFeval equals the commercial TNO solver (MFeval was matched to MF-Tyre 6.1.2.1 by its author; we have no TNO output), nor that the MF 6.2 radius model is right for a race tyre. Limits:
MFeval ran under Octave, not MATLAB (same maths, a different interpreter); the two synthetic tyres have plausible, not measured, 6.x coefficients; a coefficient is only validated in the regimes the 393 cases reach (the sweep
shows each coefficient matters somewhere, not that every combination is covered). The earlier limit "six tyres do not exercise every coefficient" is closed by the sweep below.

Two things MFeval did that a reader of its output should know:

- **Its rolling-radius loop is batch-dependent.** `while abs(Re_old - Re) > 1e-9` on a vector runs only while *all* rows are unconverged, so it stops as soon as any row converges (a standstill or no-load row does at once) and leaves
  the others at iteration 2: Re, omega, Rl, rho and Cz of a row then depend on which other rows share the call (omega off by up to 3e-5 relative in our first, batched run). The reference therefore evaluates one point per call.
- On the MF 5.2 example file (no turn-slip aligning coefficients) MFeval returns `-Inf` for Mz and Mzr at every turn-slip point (`CDrp = 0` gives `sin(0)` in a denominator); those 17 points are skipped by the test.

## Per-coefficient sweep

The golden tyres show agreement for the tyres they contain; they cannot show that a coefficient that is zero or unused in all of them is implemented right. The sweep writes, for each of the 228 coefficients of `rs::mf62`, a tyre file in which
only that coefficient differs from a base tyre, runs the unmodified MFeval on every one (one process, about one second per tyre) and compares all columns with `rs::mf62`. It also records whether MFeval's output depends on the coefficient at all
(if not, the coefficient is not validated by that tyre). Three passes, run on 2026-11-27 (Octave 8.4):

| pass | bases | tyres | what it adds |
|---|---|---|---|
| plain | MF 5.2 (Chrono Audi, FITTYP 21), synthetic MF 6.2, synthetic MF 6.1 (radius coefficients only) | 472 | every coefficient, +20 % (or a small additive step where the base value is 0) |
| dense | the two bases above with every Pacejka-type coefficient that is 0 set to 0.03 | 104 | the 52 coefficients that were inert in the plain pass: most multiply a coefficient that is 0 in the base (`RVY4..6` with `RVY1..3 = 0`, the Mx and turn-slip terms, ...), and the limits were moved outward where no case reaches |
| limits | the dense bases | 6 | `ALPMIN`, `KPUMIN`, `PRESMIN` moved inside the range the cases cover (-0.2, -0.2, 170 kPa) so the clamp engages |

Result: **582 of 582 tyres equal MFeval on every column** (1e-6 relative plus a small absolute floor, MFeval's own NaN / Inf skipped), and every one of the 228 coefficients is in at least one tyre where MFeval's output depends on it. The coefficients inert under
one version are the ones that version does not use: the MF 5.2 relaxation-length and contact-length terms (`PTX1..3`, `PTY1..2`, `LSGKP`, `LSGAL`, `Q_A1`, `Q_A2`) under 6.x, and the 6.x camber, turn-slip, Mx and radius terms under 5.2.
The sweep found no mismatch, so it changed no code; it is a statement about coverage, not a bug list.

```bash
node tools/validation/mf62_coefficient_sweep.mjs /tmp/mf62_sweep                          # plain: 475 tyre files
octave-cli --no-gui --eval "addpath('tools/validation'); mfeval_reference_dir('/tmp/mf62_sweep/tyres', 'data/validation/mf62/mf62_cases.csv', '/tmp/mf62_sweep/refs')"   # ~40 min
RS_MF62_SWEEP=/tmp/mf62_sweep core/build/rs_tests mf62_coefficient_sweep                   # prints which coefficients are inert
# the dense pass: list the inert KEYs (one per line) in dead.txt, then
node tools/validation/mf62_coefficient_sweep.mjs /tmp/mf62_sweep2 dead.txt                # same two commands on /tmp/mf62_sweep2
```

The references are 108 MB, so they are not committed (CI runs the eight golden tyres, not the sweep).

## Run MFeval and compare (the validation step)

MFeval is MATLAB code; it needs MATLAB or GNU Octave (Octave 8.4 worked: `sudo apt install octave`). The same script works in both; under Octave it calls the `+mfeval` package's `Solver` directly, because Octave resolves
`mfeval.readTIR` to the function `mfeval.m` instead of the package (the vendored files are not modified).

```bash
# Octave (Linux Mint / Ubuntu): sudo apt install octave
mkdir -p /tmp/mf62_ref
for v in 52 61 62; do
  octave --no-gui --eval "addpath('tools/validation'); mfeval_reference('tools/validation/mfeval/doc/examples/MagicFormula${v}_Parameters.tir', 'data/validation/mf62/mf62_cases.csv', '/tmp/mf62_ref/mf${v}_mfeval.csv')"
done
cmake --build core/build --target rs_tests
RS_MF62_REFERENCE=/tmp/mf62_ref core/build/rs_tests mf62_vs_mfeval
```

The example tyres are vendored in `tools/validation/mfeval/doc/examples/`. The committed golden vectors are regenerated the same way:
`node tools/validation/make_mf6x_tyres.mjs`, then `mfeval_reference('data/tires/audi_245_40R18_pac2002.tir', 'data/validation/mf62/mf62_cases.csv', 'data/validation/mf62/golden/audi_pac2002_mfeval.csv', 21)` (the 4th argument supplies the
`FITTYP` the Chrono file lacks) and the same call without it for `data/validation/mf62/tyres/opengrid_mf61_synthetic.tir` / `..._mf62_synthetic.tir`. In MATLAB run the same
`mfeval_reference(...)` call; `mfeval` itself is on the path from `tools/validation/mfeval/` (the script adds it). The case list (`data/validation/mf62/mf62_cases.csv`,
393 points from `tools/validation/mf62_cases.mjs`) covers pure and combined slip, load, camber, pressure, low speed and reverse, alpha*, turn slip, limits off,
no load / below FZMIN / above FZMAX, and slips beyond the file's limits. The comparison needs 1e-6 relative agreement on every column except `instKya`
(it depends on how rows are grouped into a call); MFeval's own NaN results are skipped and counted.

## Where this follows MFeval and where it deviates

It follows MFeval's stage order and every correction MFeval made to match the TNO MF-Tyre 6.1.2.1 solver instead of the book: Bt from the paper (A58), Dt without
abs() on QDZ3 (A60), the equivalent slip angles (A54 / A55), `s` with Fz0 (A56), `Mx` and `My` (A48) in the TNO / paper form, `t` multiplied by LFZO, the low-load
corrections of Mx and My, the low-speed model, the limits (which also gate the "E <= 1" clips), and MF 6.2's loaded radius solved by the secant method.

Deliberate **deviations**, all for inputs where MFeval returns NaN or complex numbers (marked `DEVIATION` in `mf62.cpp`):

- turn slip with exactly `phit = 0` gives `acos(0/0)` in MFeval, hence NaN for Mz: here zeta7 = 1;
- turn slip at exactly `Vx = 0`: MFeval's `sign(0) = 0` makes `BHyp = Inf` and Fy NaN: here the sign is +1, as MFeval itself does for its `Vc_prime`;
- turn slip with no load: `BDrp = 0/0`: here the spin torque is 0;
- MF 5.2 / 6.1 deflection with `Q_FZ2 = 0` (no quadratic term) is solved linearly, the secant solver stops on a zero slope, and the iteration for omega is capped at 100 steps;
- FITTYP 5 is accepted as the MF 5.2 / PAC2002 family (the four FEDA truck tyres declare it); MFeval accepts 6, 21, 61 and 62 only.

## What the original source showed (the Julia port differs)

MFeval.jl (MIT) was the first cross-reference, but `Solver.m` differs from it in places, and `mf62.cpp` follows `Solver.m`: `phit * cos(alpha)` is applied first with the original
alpha; the pressure used for the rolling-radius estimate is the limited one; output column 10 is the processed `phit`; the output `muy` is forced positive when the limits are on;
`Fz_lowLimit` applies FZMIN even at zero load (the aligning moment then zeroes it); the "E <= 1" clips run only with the limit checks on; `LKYC` multiplies the whole MF 5.2 camber
stiffness; the turn-slip aligning moment has real `zeta7` / `zeta8` terms (MFeval.jl has placeholders); and the "Fy0 at gamma = 0" inside Mz keeps turn slip on.

## How this compares with the game's current tyre (`rs::magic_formula`)

Read against the MFeval source, the game's tyre is the MF 5.2 pure-slip equations with parts of the 6.x terms, its own combined-slip weighting, and its own contact-patch / thermal / carcass models.
Differences that matter for anyone calling it "MF 6.2" (each checked in `core/src/tire.cpp`):

- the "MF 6.2 hybrid" flag adds a hand-tuned `0.022 * gamma` camber shift to the kappa-induced weighting `Gyk` (`shyk`): not a Magic Formula term;
- after the weighting functions (which are normalised by `Gxa0` / `Gyk0`, as in MF 6.x) a friction-ellipse clamp trims Fx and Fy; the Magic Formula has no such step;
- `Mx` has 4 of its 14 `qSx` terms (`qSx1..3`, `qSx13`, plus `pPmx1`);
- the "MF 6.2 loaded radius" (`effective_rolling_radius_mf62`) is a hand-tuned camber term (0.042 / 0.011) and a force term; the real MF 6.2 radius is the secant-solved `Q_CAM1..3`, `Q_FYS1..3`, `Q_FCY2`
  relation, and the game's tyre has none of those coefficients;
- the aligning moment is close to the MF 6.x form but differs in details (the pressure term has the opposite sign convention, `Fz0` instead of `Fz0'`, no `LTR` and no `t * LFZO`);
- `pEy5` is part of the plain MF 6.1 `Ey`, not a 6.2 extension.

None of this says the game's tyres feel wrong: peak grip is a per-car calibration (docs/physics.md section 0). It says the claim "full MF 6.2" cannot be made for the runtime tyre, and that `rs::mf62` is the way to a real one.

## A/B against the game's tyre

`core/tests/test_mf62_ab.cpp` evaluates the game's `rs::magic_formula` and `rs::mf62` on the SAME real tyre file. The game's `TireParams` come from the test's `.tir` mapping (`tir_loader.hpp`, the same symmetric single-fit subset the game's
own `tools/tir2car.mjs` makes: it zeroes PEY3, QBZ4, QDZ3, QEZ4, QHZ1/2, PHY1/2, PVY1/2, QDZ6/7, SSZ1 and replaces the combined-slip coefficients by neutral defaults), so a difference is the model plus that mapping, not a different tyre.

Tyre level (nominal load, 16.6 m/s, game / full MF, 1.00 = identical), ten Chrono tyres: peak grip `mu_x` 1.000, `mu_y` 1.02 to 1.04, slip stiffnesses `C_alpha` and `C_kappa` 1.000 to 1.002, load sensitivity 0.99 to 1.14. So the
pure-slip curves are the file's. Where they are **not**: the self-aligning moment at 3 deg is 0.62 to 4.08 times the full MF's depending on the tyre, and the camber force at 3 deg is 0.22 to 1.38 times. Those are the dropped terms.
With the same call, signs of Fx (from kappa), Fy and Mz (from alpha) and Fy (from camber) agree (`mf62_bridge_signs`); the file's own combined-slip and shift terms give a small Fx at pure alpha (about 100 N) and Fy at pure
kappa (about 30 N) that the game's neutral defaults drop, and Chrono's files have no overturning-moment coefficients, so the full-MF tyre's Mx is 0 where the game's own defaults give about 20 N m.

Car level (Chrono Audi 245/40 R18 on both axles, radius / inertia / load rating from the car; A = game tyre, B = full MF):

| car | 0-100 km/h A / B | 60-0 mph A / B | skidpad A / B | AI lap of the 12 m-corner block A / B |
|---|---|---|---|---|
| Tornado GT3 | 3.22 / 3.18 s | 32.1 / 32.1 m | 0.963 / 0.996 g | 40.4 / 40.6 s |
| Kestrel GT | 4.75 / 4.70 s | 34.5 / 34.5 m | 0.923 / 0.993 g | 41.7 / 41.6 s |

Braking is identical, launches are within 1.5 %, the AI lap within 0.6 %. The steady cornering limit is 3 to 8 % higher on the full MF. The cause is **not isolated**: the tyre-level peak grip is the other way round (game 2 to 4 % higher),
so the difference sits in what the skidpad adds to pure slip (tractive force at the limit, camber, the game's friction-ellipse clamp, the weighting of combined slip); the A/B shows it, it does not say which tyre is closer to a real one.
The AI lap is a weak test of grip: the AI plans its corner speed from a fixed friction assumption (32 km/h in the 12 m corners), never reaching the tyre limit, so it shows that the full-MF tyre does not upset handling, nothing more.

## The opt-in flag

`TireParams::mf62` (a shared `rs::mf62::Params`) is filled when the car JSON's tyre block has `"mf62_tir": "tires/<file>.tir"` (relative to the data folder, or absolute) in `load_car_config`. When set and the contact has no kerb height map, `magic_formula()` takes
Fx, Fy, Mx, Mz, the pneumatic trail and the patch length from `rs::mf62` instead of the game's model. Signs are converted (alpha = -atan(tan_alpha), gamma = -gamma). The game's surface / temperature / wear grip arrives through `mu_scale` as before; the
bridge applies the game's Stribeck sliding-speed decay and 3-rib thermal grip and stiffness (a helper moved out of `magic_formula_base`, same code, shared by both paths), and scales the file's peak friction (`LMUX`, `LMUY`) with it.
**Not** in the full-MF path: the 4x4 contact patch with kerbs (a height map falls back to the game's tyre), the cold-tyre chatter and the adhesion ratio the game's other systems read.

No shipped car has the key (`mf62_car_flag` checks five), so every shipped car is unchanged: `rs::magic_formula` on four cars, both axles, hybrid and patch grid on and off, with and without a tyre condition, 1,752,192 evaluations, gives the same
64-bit fingerprint on `HEAD` and on this tree. Only `load_car_config` (the native tests and tools) reads the tyre file. The browser bridge (`web/wasm/bridge.cpp`) and the Unreal component (`OpenGridVehicleComponent.cpp`) build the car from JSON **text** with `parse_car_config`, which has no data folder, so they leave `TireParams::mf62` empty and silently keep the game's tyre even when the key is present. A host that wants the full-MF tyre has to hand the file's text to `mf62::parse_tir` and set `TireParams::mf62` itself; no host does yet.

## Cost

One `rs::mf62::evaluate()` (all 30 outputs) against one game `magic_formula()` on this machine (the 8 GB laptop, one core, 200,000 calls each): game 333 ns, `rs::mf62` on a PAC2002 file 669 ns, with the MF 6.2 secant radius 952 ns. At 4 wheels x
240 Hz that is 0.3 / 0.6 / 0.9 ms of tyre time per simulated second: under 0.1 % of a 30 fps frame budget. WebAssembly and the Unreal build were not timed.

## Default

The full-MF tyre stays **off by default**. Reasons, none of them performance: no shipped car has real tyre data (the calibrated race tyres are the game's own, far grippier than a Chrono road tyre: the Tornado GT3 stops from 60 mph in 21.3 m on its own tyre, 32.1 m
on the Audi file), the mapping and the full MF differ in aligning moment and camber in ways the A/B shows but cannot rank, and the full-MF path has no kerb patch. Switching a car on is one JSON key once a real tyre file exists for it.
